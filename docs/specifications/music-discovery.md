# チャートとプレイリスト推薦の仕様案

作成日：2026年11月4日。対象：SyncTune Hub。状態：一部実装済み、推薦エンジンは提案段階。

2026年11月5日に、Last.fm／YouTube Data APIを独立した任意連携として導入した。
設定画面からキー・地域・有効／無効を指定でき、「見つける」でYouTubeの人気音楽動画とLast.fmの国別人気曲を閲覧できる。
Last.fmの類似曲は入力した曲名・アーティスト名から手動で検索する。
API由来の候補からは提供元のページを開き、取得や同期を自動で始めない。
以下に記載するプレイリスト単位の候補生成・評価・推薦理由・フィードバックは、今回の導入には含まない。
導入手順・保存・呼出し上限は[README](../../README.md#人気の音楽類似曲を探す任意)を参照。

プレイリストを同期して持ち出す現在の体験に、「次に聴きたい曲やプレイリストを見つける」入口を加える。チャートの表示と、選んだプレイリストからの推薦を提供する。推薦理由とデータの出典を見せ、候補の閲覧だけで取得や同期を始めない。プレイヤーは現在の小さい試聴用の表示を維持する。

## 1. 実現できる範囲と採用方針

| 体験 | 実現方法 | 初期方針 |
| --- | --- | --- |
| いま人気の音楽動画を知る | YouTube Data APIの公開動画チャート | API利用用途の確認後に追加。公式週間楽曲ランキングとは別の表示にする |
| YouTube公式の楽曲チャートを見る | 公式サイトへのリンク、利用条件を満たす配信・インポート元 | 正確な地域・期間・順位を取得できるソースだけを公式チャートとして表示 |
| このプレイリストに合う曲を探す | ローカルの曲情報と明示的な好み、任意の外部類似曲サービス | 主機能として採用。再生履歴やGoogleログインがなくても開始できる |
| 別のプレイリストを提案する | 登録済み・提供元が許可する候補リストとの相性評価 | 曲の推薦に続いて対応。候補の実在と現在の公開状態を確認する |
| YouTube本体のおすすめを複製する | 公開Data APIでは同等の入口を前提にできない | 標準仕様に含めない |
| おすすめを自動で大量取得する | 権利・提供条件、容量、誤同定への対応が必要 | 初期は候補選択と確認を経て登録する |

YouTubeの週次Top Songsは、楽曲の複数の公式な利用形態を集計する。単一動画の人気とは集計単位が違う。Data APIの `mostPopular` も2025年7月21日に取得対象が変わっている。両者を同じ「ヒットチャート」として表示しない。[公式チャートの説明](https://support.google.com/youtube/answer/9014376)、[API変更履歴](https://developers.google.com/youtube/data/revision_history)。

## 2. ストリーミングサービスの仕組みと取り入れる点

一般的な推薦は、候補を集め、好みに合う順に評価し、重複や偏りを調整する構成を取る。Googleの教材はこの3段階を説明している。YouTubeの2016年の公開論文も候補生成とランキングを分けているが、現在の内部実装をすべて説明する資料ではない。[Googleの推薦システム教材](https://developers.google.com/machine-learning/recommendation/overview/types)、[YouTubeの公開論文](https://research.google/pubs/deep-neural-networks-for-youtube-recommendations/)。

| 方法 | 使う情報 | このアプリでの使いどころ |
| --- | --- | --- |
| 編集・チャート | 人が選んだリスト、地域や期間ごとの流行 | まだ好みが分からない初回の入口 |
| 内容に基づく推薦 | アーティスト、ジャンル、年代、楽曲の特徴 | 選んだプレイリストとの相性。小規模でも開始できる |
| 協調フィルタリング | 多くの利用者の聴取・保存などの共通傾向 | 外部サービスの類似曲情報を任意に利用。家庭内の少数履歴だけで大規模な学習を行わない |
| 行動に基づく個人化 | 保存、お気に入り、実際の聴取、明示的な拒否 | 利用が進んだ後の調整。短い試聴や通信失敗を嫌いと解釈しない |
| 多様性の調整 | 同一アーティストの偏り、既知曲と新規曲の割合 | 同じ曲やアーティストばかりになることを防ぐ |

Spotifyは編集者による選曲と個人向け推薦を組み合わせ、聴取・検索・スキップ・保存などを好みの情報に使うと説明している。この考え方を、プレイリスト単位の目的と利用者の明示的な選択に落とし込む。[Spotifyの推薦の説明](https://www.spotify.com/uk/safetyandprivacy/understanding-recommendations)。

Spotify自身の推薦機能が、そのまま新規アプリから利用できるわけではない。2024年の変更で新規用途のRecommendations等へのアクセスが制限され、現在の開発モードにも条件があるため、中核の依存先にしない。[Spotify APIの変更](https://developer.spotify.com/blog/2024-11-27-changes-to-the-web-api)、[開発モードの条件](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)。

Apple Musicには利用者トークンを必要とする推薦リソースのAPIがある。連携する場合はApple側の認証と曲IDの対応付けが必要になる。[Apple Musicの推薦API](https://developer.apple.com/documentation/applemusicapi/get-multiple-recommendations)。ListenBrainzも協調フィルタリングの推薦APIを公開しているが、文書上は実験的なAPIであり、独立した任意プロバイダーとして扱う。[ListenBrainzの推薦API](https://listenbrainz.readthedocs.io/en/latest/users/api/recommendation.html)。

## 3. 取得元の設計

### チャート

最初の地域は日本とし、設定で変更できるようにする。IPアドレスから好みや地域を決めない。

1. **現在の人気音楽動画**：`videos.list` の `chart=mostPopular`、`regionCode=JP`、音楽カテゴリ、最大50件。公開情報の取得はAPIキーを使用し、個人向けOAuthを必須にしない。対象地域・カテゴリが非対応なら利用不可と表示する。YouTubeの応答順を維持し、週間楽曲順位や独自の再生数伸び率に変換しない。
2. **公式の楽曲・MVチャート**：提供元が許可する取得方法とデータ形式を確立してからアダプターを有効にする。それまでは公式サイトへの導線を提供する。非公開APIやHTML解析を標準の取得経路にしない。
3. **登録した公開プレイリスト**：既存のURL追加を利用できる。所有者を確認できる場合も、プレイリストの並び順がチャート順位と同じとはみなさない。未検証のリストには「登録されたプレイリスト」と表示する。

各ソースは `source_id / provider / region / chart_kind / ranking_semantics / period_start / period_end / published_at / fetched_at / expires_at / source_url` を持つ。期間がない情報に週間ラベルを付けず、APIの地域指定に架空の `GLOBAL` を渡さない。世界チャートは対応を確認したソースだけに出す。[videos.listの仕様](https://developers.google.com/youtube/data/reference/rest/v3/videos/list)。

「最新」は取得時刻と集計期間の両方で示す。通常は6時間ごとに更新確認し、更新中・取得失敗・期限切れを区別する。失敗しても前回成功分を空配列で上書きしない。表示可能期限を過ぎたデータはおすすめの入力から外し、出典へのリンクと更新案内を残す。

### 外部の類似曲と曲情報

- **Last.fm**：`track.getSimilar` を優先し、曲を同定できない場合に `artist.getSimilar` を使う。APIキーは必要だが、これらの照会に利用者のLast.fmログインは不要。API利用条件を満たす個人向け連携として任意に有効化する。[類似曲](https://www.last.fm/api/show/track.getSimilar)、[類似アーティスト](https://www.last.fm/api/show/artist.getSimilar)。
- **MusicBrainz**：アーティストや録音のID、版の確認などの補助に使う。推薦エンジンそのものとは扱わない。公開サービスの制限に従い、1秒に1回以下と識別できるUser-Agentを使う。[MusicBrainzのレート制限](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting)。
- **ytmusicapi**：チャートや次の曲、プレイリスト候補を取得する機能はあるが、ブラウザのリクエストを模倣する非公式ライブラリである。標準依存にせず、技術検証対象として記録する。認証・仕様変更への追随とYouTube側の許諾を解決できる場合に限り別途判断する。[プロジェクトの説明](https://ytmusicapi.readthedocs.io/en/stable/)。

外部連携を切っていても、ローカルの候補から推薦できる。外部照会を有効にする際は、送信する曲名・アーティスト名またはIDを案内する。プレイリスト名、全履歴、音声ファイルをまとめて外部送信しない。

## 4. データ利用と再生の境界

YouTube APIの規約は、無許諾の映像音声保存・オフライン提供、非公開APIやAPIデータの派生利用を制限し、保存データの更新・削除にも条件を設けている。[YouTube Developer Policies](https://developers.google.com/youtube/terms/developer-policies)。

本案の標準操作は出典の閲覧と権利・提供条件を満たすローカル音源の推薦とする。API由来の候補を既存のyt-dlpへ自動投入しない。APIデータを特徴量にする機能は用途を確認してから有効にする。キーや処理経路の分離だけで条件を満たしたとは判断しない。

プロバイダーごとに、表示・キャッシュ・推薦入力・音源取得の許可を分けて管理する。YouTube由来の表示とアプリ独自のおすすめを区別する。YouTube APIデータは、適用される期限に従って更新または削除し、汎用キャッシュの上限を30日以内に設定する。認証解除や削除要求では関連キャッシュと推薦入力も無効化する。

Last.fmの表示は出典へのリンクと指定された帰属表示を含め、HTTPのキャッシュ指示に従う。キャッシュの初期容量上限は20MBとし、契約上の上限を超えない。商用化・公開提供など利用形態が変わる場合は条件を再確認する。[Last.fm API利用条件](https://www.last.fm/api/tos)。

## 5. 利用者が使う画面

メインナビゲーションに「見つける」を追加する。起動時に開く画面は現行の同期を維持し、新しい画面のデータは訪問したときに取得する。同期詳細には「このプレイリストからおすすめを探す」を置き、選択状態を引き継ぐ。

```text
見つける
  もとにするもの  [集中する時間 ▼]  [バランス ▼]
  探す範囲        [ライブラリ内 / 外の曲も含める]

  このプレイリストから
    曲A  /  アーティストA
    理由：登録曲Bと同じアーティストの、まだ入っていない曲
    [試聴] [リストに追加] [興味なし]

  日本のチャート・人気動画
    取得元 / 集計期間 / 最終確認 / 更新状態
    曲や動画ごとの出典リンク

  合いそうなプレイリスト
    含まれるアーティスト、登録済み曲、提案した理由
    [内容を確認]
```

- 初期表示は20件、最大60件まで追加表示。画面全体を作り直さず、条件・展開・スクロールを維持する。
- 所有している再生可能ファイルは「試聴」、未取得の外部候補は「YouTubeで開く」「音源を選ぶ」を表示する。埋め込みを採用する場合も明示操作後に読み込む。
- 「リストに追加」はローカルの聴取リストへの登録であり、自動ダウンロードやYouTube上のプレイリスト書き換えではない。必要な外部操作は別の確認画面で内容を見せる。
- ライブラリ内にある、選択元に既にある、版違い、情報未確認を区別する。曲の「興味なし」は元のファイルを削除しない。取消できるようにする。
- おすすめが作れない場合は、曲情報の確認、別のプレイリストの選択、チャートの閲覧を案内する。人気順を個人向け推薦と偽って埋めない。
- プレイヤーの常時大型表示や自動再生は加えない。

## 6. 推薦の処理

### 入力と曲の同定

同期プレイリスト、ローカルの聴取リスト、明示的に選んだ曲を起点にする。初期は単一のローカル利用者プロファイルとし、YouTubeアカウントや端末の所有者から好みを推測しない。家庭内で共有する場合はプレイリスト単位の文脈を優先する。

動画・ファイルと楽曲を分けて管理する。同じ曲のMP3とFLACは同じ録音の再生候補だが、ライブ、カバー、リミックス、再録音は区別する。録音IDやISRC、曲名、アーティスト、版、長さを合わせて確認し、単一の文字列一致だけで統合しない。

曲情報には出典と確信度を付ける。投稿チャンネル名を歌唱アーティストと同一視しない。曖昧な情報は利用者が修正でき、確認できない曲を強い推薦理由に使わない。種となる曲は最大20曲、1アーティストあたり最大2曲を初期値とし、大きいリストの一部に偏ることを抑える。

### 候補生成と評価

1. ローカルの未登録曲、同じアーティストの別曲、許可された外部の類似曲、確認済みの候補プレイリストから最大500候補を集める。ソースごとの利用可能範囲を先に適用する。
2. 候補の実在、曲情報、利用可能な再生先を確認し、同一録音・同一動画の重複と明示的な拒否対象を除く。
3. 利用が認められる情報だけで、起点との近さ、明示的な好み、新しさを評価する。初期は説明可能なルールと内容ベクトルを使い、GPUや大規模学習を必須にしない。
4. 「近い曲」「バランス」「新しい発見」の3モードで並びを調整する。バランスは既知に近い候補7割、探索候補3割を目安とする。候補が足りない場合に水増ししない。
5. 上位20件で同じ主アーティストは原則3件まで、連続は2件まで。既に選択元にある録音は除く。探索を希望しない場合は外部候補を混ぜない。

同じアーティストである根拠、利用を許可された類似曲情報、ジャンルの一致など、実際に使った情報から推薦理由を組み立てる。根拠がない「好きなはず」「好みに98%一致」といった表示はしない。外部サービスの類似度を、そのまま好みの確率として表示しない。

LLMは初期要件にしない。後から導入する場合も、曲情報の補助や説明の生成に用途を限定する。実在する候補IDの範囲から選ばせ、架空の曲・URL・音楽特徴を生成した結果は採用しない。外部モデルを使う場合の送信範囲は設定から選べるようにする。

### プレイリストの推薦

候補は、登録済みリストと許可された外部ソースに限定する。利用できる曲情報に基づく共通アーティスト、録音の重なり、ジャンル、まだ持っていない曲の割合を評価する。利用権限の確認できないYouTube API由来の情報はこの計算に混ぜない。内容が未確認の外部リストは、おすすめとして断定せず「候補」と表示する。

独自に作る聴取リストは、生成時の曲目を固定したリストとして保存する。後から「作り直す」を選んだ場合も差分を確認する。毎日の再計算で曲目や保存済みファイルを勝手に置き換えない。

## 7. 再生履歴とフィードバック

初期版は履歴なしで動作し、「追加」「お気に入り」「興味なし」を強い信号にする。短い試聴、ファイル取得、通信切断、同期失敗は嫌いという信号にしない。

後続版では `session_id / event_id / recording_id / action / listened_ms / occurred_at / context` を記録する。実際に流れた区間を加算し、シークした先までを聴取済みと数えない。イベントの重複送信を防ぎ、30秒以上などの閾値は初期仮説として評価する。再生完了は長さを確認できる場合に限る。

Syncthing先で別のアプリを使って聴いた事実は、ファイル同期からは分からない。「このアプリ内の再生」と明示し、履歴が届かない端末を未聴取・低評価と扱わない。外部履歴やListenBrainzの送信は任意の別連携にする。履歴の保存停止・削除と、明示的な好みのリセットを設定画面から行えるようにする。

## 8. 現在の実装との接続

| 現状 | 必要な変更 |
| --- | --- |
| `Track` と `PlaylistSyncTrack` に曲が分かれている | 両方を参照する共通の録音・再生先モデルを追加。既存の保存パスとIDは維持 |
| 曲情報の `artist` に投稿者が入る経路がある | 曲のアーティストと投稿者を区別し、利用者の訂正と出典を保持 |
| `/stream/{id}` でHTTPリクエストごとに `play_count` を加算する | Range取得やシークで増える旧値を推薦に転用せず、実聴取イベントを別に記録 |
| 同期トラックのストリームには同等の聴取記録がない | 同じイベント契約を両方の再生経路に適用 |
| 任意に編集する聴取リストのモデルがない | 同期元を変更しないローカル聴取リストを追加 |
| `youtube_api_service.py` はアカウントとプレイリスト取得が中心 | 公開情報用の接続、プロバイダー単位の予算・利用条件を追加 |
| 追加のプレビュー・確定とプロファイルがある | 選択→内容確認→確定という操作を再利用。提供元が許す操作だけ接続 |
| 画面単位の遅延読み込みとページ表示がある | 「見つける」も訪問時に取得し、画面を離れたらポーリングを止める |

変更候補は `backend/app/api/discovery.py`、`services/discovery/`、`tasks/discovery.py`、`frontend/js/discovery.js`。既存の `models.py`、`player.js`、ナビゲーション、設定画面に接続する。以下のモデルは新規設計であり、現在ある機能とは区別する。

- `Recording`：録音の同定、版、アーティスト、出典、確信度。
- `MediaRef`：録音に対応する既存の `Track` / `PlaylistSyncTrack` と外部URL。欠損ファイルは利用不可として扱う。
- `ListeningPlaylist / ListeningPlaylistItem`：同期設定と独立した聴取リスト。
- `DiscoverySource / DiscoverySnapshot / DiscoveryItem`：取得元、集計期間、キャッシュ期限、提供元ID、出典。
- `RecommendationRun / RecommendationItem`：入力の版、使用ソース、アルゴリズム版、結果、理由。
- `Feedback`：対象とプレイリスト文脈、肯定・拒否・取消。
- `ListenEvent`：後続版の実聴取イベント。旧再生回数は移行して精密な履歴に見せない。

API案：

| API | 内容 |
| --- | --- |
| `GET /discovery/sources` | 利用できる取得元と設定・障害状態 |
| `GET /discovery/charts` | ソース・地域・種別・期間でチャートを取得。最大20件ずつ |
| `POST /discovery/sources/{id}/refresh` | 更新ジョブを依頼。重複と予算超過を防ぐ |
| `POST /discovery/recommendation-runs` | 起点、モード、候補種別、探索範囲で生成。ジョブIDを返す |
| `GET /discovery/recommendation-runs/{id}` | 結果、理由、更新日時、状態、入力の版を取得 |
| `POST /discovery/feedback` | 好み・拒否・取消を重複なく保存 |
| `POST /listening-playlists/preview` と `/commit` | 選んだ録音から聴取リストを確定 |
| `POST /listening-events` | 後続版の実聴取イベントをまとめて受信 |

## 9. 運用と性能

FastAPIの要求中に大量の外部検索や学習を行わない。Celeryの `discovery` キューで生成し、初期並列数は1。同期やダウンロードのキューが詰まらないよう分離する。生成の識別子は起点の版・条件・好みの版・アルゴリズム版から作り、同じ依頼をまとめる。

チャートは6時間、動画表示情報は24時間、推薦結果は24時間を初期上限とする。外部データの期限・HTTP指示が短ければそちらを優先する。起点の編集、拒否、情報の訂正では関連する推薦を直ちに無効化する。利用条件に依存する履歴の長期蓄積は初期版に含めない。

2026年6月からYouTube APIの一部に独立したクォータ枠が導入されている。現在の文書では `search.list` は検索枠の1回1単位、標準100回/日とされる。古い「1回100単位」を前提にせず、実際のプロジェクトの割当を設定画面で確認できるようにする。[変更履歴](https://developers.google.com/youtube/data/revision_history)、[search.listの仕様](https://developers.google.com/youtube/data/reference/rest/v3/search/list)。

動画IDが既にある候補は検索せず、表示情報をまとめて確認する。外部の曲名からYouTube動画への対応付けは必要になった候補だけに行い、検索のアプリ内初期予算は20回/日とする。未解決でも曲の候補は表示でき、外部サイトで探す導線を使える。割当超過時に別キーや非公開APIへ切り替えない。

外部通信の初期同時数は2、タイムアウトは10秒。429はRetry-Afterを守り、指数的に間隔を空ける。ソースの失敗と空の推薦結果を区別する。鍵とトークンはサーバーだけに置き、画面・ログ・配布設定へ値を返さない。再作成しても候補・好み・取得元設定を維持する。

性能目標は、1万曲のライブラリと最大500候補で計測し、キャッシュ済み結果のAPI応答p95を300ms以内、ローカル生成を5秒以内とする。いずれも初期の受け入れ目標であり、現時点の実測値ではない。

## 10. 段階と受け入れ条件

| 段階 | 提供する内容 | 完了条件 |
| --- | --- | --- |
| P0 取得元と曲情報の検証 | 代表的な日本語・英語・ライブ・カバーの曲を同定。チャートの取得条件と表示内容を確認 | 利用可能なプロバイダー、操作、必要なキー、対象外の取得元が確定する |
| P1 最初の「見つける」 | ローカルの聴取リスト、プレイリスト起点の曲推薦、理由、拒否と取消。対応を確認したチャート・人気動画の入口 | 履歴やOAuthがなくてもローカル推薦が動き、見た候補が勝手に取得されない |
| P2 外部の発見 | 任意の類似曲連携、別プレイリストの候補、版の確認、取得元別の障害表示 | 候補の実在と出典を検証し、重複登録・誤同定・外部停止から復帰できる |
| P3 聴取に合わせた改善 | 実聴取イベント、文脈別の調整、任意の外部履歴 | シークや通信再試行で履歴が増えず、外部端末の未観測を誤判定しない |

最初はローカル推薦とチャートの入口を同時に作り、YouTube API利用が未確定でも公式サイトへの導線とローカル機能は提供できるようにする。非公式接続や大規模モデルをP1の前提にしない。

実装ごとに、以下の回帰テストを追加する。

- 曲名だけが同じ曲、版違い、同じ録音の複数形式を正しく扱う。投稿者だけではアーティストを確定しない。
- 既存曲と拒否した曲を除外し、拒否取消で戻せる。根拠が欠ける場合に説明を作らない。
- 公式チャート、人気動画、ユーザーのリストでラベル・順位・期間を取り違えない。更新失敗時に前回成功分を壊さない。
- 画面の表示前や離脱後は追加の取得をせず、遅い応答が別の条件の結果を上書きしない。
- 予算・期限・キャッシュ指示・出典表示を守り、許されない音源取得や外部送信を起動しない。
- 大量曲で全組合せを計算せず、既存の同期と再生が並行して動く。コンテナ再作成後も状態を保持する。
- スマホとPCで、候補の確認→理由の理解→追加または拒否→取消を試せる。プレイヤーが画面を占有しない。

推薦品質は、用途の違う3つのプレイリストで上位10件を評価する。「聴いてみたい曲が3曲以上」を初期の利用者テスト目標にし、重複ゼロ、拒否した曲の再表示ゼロを確認する。数値は保証ではなく改善判断の目安とする。表示件数やダウンロード件数だけを成功指標にしない。
