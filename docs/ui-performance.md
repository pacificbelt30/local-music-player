# 既存機能の使い勝手・性能改善

2026-11-03に同期一覧、ダウンロードキュー、保存済みファイルを確認し、以下を修正しました。

| 対象 | 従来の問題 | 修正後 |
| --- | --- | --- |
| 同期一覧の更新 | プレイリストごとに全曲のORMオブジェクトを取得して件数を数える | DB側でまとめて集計。曲数やプレイリスト数によらず一覧のSQLは2回 |
| DL進捗の配信 | async処理の中で同期DB・Redis・Celery通信を行い、進捗は1曲ごとにRedisへ問い合わせる | 通信とDBセッションをワーカースレッドに隔離し、進捗は1回のMGETでまとめて取得。中断確認はストリームごとに30秒間隔 |
| ファイル削除・検索・続きの読み込み | 削除のたびに先頭50件へ戻る。取得失敗や検索結果ゼロの理由が分かりにくい | 削除した行だけを除き、位置とページを維持。検索やページ取得との競合を処理し、失敗理由と再試行を表示 |
| DL再試行・取消・URL登録解除 | 通信失敗を隠す、連打できる、更新のたびに全行を作り直す | 操作中の重複を防止し、失敗理由をその行に表示。同じ行のDOMと他の行のフォーカスを維持 |

キューは処理中のジョブを優先して表示します。古い失敗が200件以上あっても処理中のジョブが埋もれません。一覧と進捗の対象を同じ最大200件にそろえ、対象外ジョブによる無駄な再取得を防ぎます。

進捗の接続が切れた場合は、最後に取得した表示であることを案内し、自動再接続時に一覧を更新します。ブラウザのタブを隠したときとページ離脱時は接続を閉じ、戻った際に1本だけ再接続します。

ファイルの並び順にはIDを補助キーとして使い、同じ保存日時のファイルが複数あってもページ間で重複・欠落しないようにしました。APIの取得件数は1〜200件に制限します。新規ファイルの追加や外部操作を含む完全なスナップショットページングではありません。

## 検証

- メモリ上のSQLiteで40プレイリスト・6,000曲を使った同一条件の計測では、一覧のSQLは41回から2回、展開した曲オブジェクトは6,000件から0件、処理時間は約70msから約5msになりました。時間はこの検証環境の参考値です。
- 100件の進捗取得がRedisへの1回の通信で済むこと、200件の表示範囲、セッションの後処理、イベントループが他の処理を実行できることを回帰テストで確認します。
- 実API・Redisコンテナでは、進捗配信中にRedisを5秒待たせても別APIが2秒以内に応答すること、進捗配信が再開することを確認します。通常のCIでも実行します。
- DOMテストでは二重操作、通信失敗、再接続、古い応答、検索と削除の競合、ページ読み込み中の削除、全表示行の削除後も続きが読めることを確認します。
- Chromiumで1440px・390px・320px幅とダーク表示を確認。100件読み込み後の削除で、残る行のDOMとスクロール位置が維持されること、横にはみ出さないことを確認しました。

## 次に調べる対象

以下はコード上で残っている処理です。利用規模に応じた計測を行ってから変更します。

- 同期詳細は曲の一覧全体を取得するため、数千曲のプレイリストで転送量と描画時間を計測する。ページ分割と一覧内検索が候補。
- 初期表示では非表示のファイル・設定画面のAPIも取得する。タブごとの遅延読み込みで起動時の通信を減らす余地がある。
